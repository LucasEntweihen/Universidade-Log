FUNDAMENTOS

O ciclo de vida não é burocracia: é proteção

Foto: Peter Thomas em Unsplash

É tentador tratar onPause, onStop e onDestroy como cerimônia obrigatória do Android. Na prática, eles existem porque o sistema pode matar o processo do seu app a qualquer momento em segundo plano pra liberar memória: sem avisar, sem pedir licença. O que estiver salvo até onPause sobrevive; o que não estiver, se perde.

Isso muda a forma de pensar sobre Intents também. Um Intent explícito (você nomeia a Activity exata) é previsível e rápido. Um Intent implícito (você descreve a ação: "compartilhar texto", "abrir link") delega ao sistema decidir qual app responde, e se mais de um puder, o usuário escolhe. É basicamente uma forma de acoplamento fraco entre apps diferentes no mesmo aparelho.

Um detalhe que evita bug silencioso

O Bundle que acompanha um Intent tem limite de tamanho: é pensado pra IDs, textos curtos e flags, não pra listas grandes ou bitmaps. Ultrapassar esse limite gera uma TransactionTooLargeException, que só aparece em certos aparelhos, tornando o bug difícil de reproduzir em desenvolvimento.

MÓDULO 01

Densidade de tela, sem mistério

Foto: Ingmar em Unsplash

A fórmula por trás do dp é simples: px = dp × (dpi / 160). Isso significa que numa tela de 240 dpi, 1 dp equivale a 1,5 pixel físico: e é exatamente essa conversão automática que impede um botão de parecer enorme num aparelho e minúsculo em outro. O Android trata 160 dpi como densidade de referência (a antiga categoria "mdpi"), e todas as outras densidades (hdpi, xhdpi, xxhdpi, xxxhdpi) escalam a partir dela.

Vale reforçar um detalhe que passa despercebido: se o app manipula bitmaps diretamente ou responde a gestos contando pixels cruzados pelo dedo, é preciso converter esses valores para dp antes de fazer a lógica: trabalhar direto em px nesses casos reintroduz o mesmo problema de inconsistência entre aparelhos que o dp existe pra resolver.

Por que ConstraintLayout compensa o esforço

Layouts aninhados (LinearLayout dentro de LinearLayout dentro de RelativeLayout...) forçam o sistema a medir a árvore de views várias vezes. O ConstraintLayout resolve isso com uma hierarquia plana: cada view se ancora diretamente em constraints, guidelines ou barriers, sem depender de containers intermediários. Isso tende a reduzir profundidade de hierarquia e o tempo de medição/layout em telas complexas.

Um recurso que poucos exploram no começo: barriers. Uma barrier se posiciona dinamicamente com base no maior (ou menor) entre dois ou mais elementos: útil quando você não sabe de antemão qual view vai ter o texto mais longo, e quer que outras views se alinhem a ela de qualquer forma.

MÓDULO 02

Por que "tema" e "estilo" não são a mesma coisa

Foto: Nastia Petruk em Unsplash

Um style define atributos para um tipo específico de view: por exemplo, "todo botão primário usa esta fonte e este padding". Um theme vai além: define um conjunto de recursos nomeados semanticamente (como colorPrimary) que podem ser referenciados por qualquer style, layout ou widget do app inteiro, quando aplicado via android:theme numa Activity ou no elemento <application> do Manifest.

A ideia de dar nomes semânticos aos recursos (em vez de usar valores fixos) é o que torna o dark mode possível sem reescrever nenhum layout. O app troca só a definição de colorPrimary ou windowBackground por trás do nome; a estrutura dos styles continua igual. É praticamente o mesmo princípio de variáveis CSS custom properties na web.

Escopo importa

Se você aplica um style diretamente a um ViewGroup (um container), os filhos não herdam essas propriedades automaticamente: só a própria view recebe o style. Para que o efeito se propague para todas as views dentro de uma Activity, é preciso aplicá-lo como tema, não como style pontual.

MÓDULO 03

MVVM na prática: e uma pegadinha da Translation API

Foto: Emma Swoboda em Unsplash

Na documentação oficial de arquitetura do Google, o ViewModel é descrito como um state holder: ele deve viver pelo mesmo tempo que a UI que representa. Isso é o que garante que ele sobreviva a uma rotação de tela: a Activity é recriada, mas o ViewModel associado a ela continua o mesmo objeto na memória, então nenhuma chamada de rede precisa ser refeita nem nenhum dado se perde.

O Repository entra como fonte única de verdade: ele decide se os dados vêm da rede, de um cache local ou de um banco, e expõe isso de forma unificada. A ViewModel nunca deveria saber se por trás existe Retrofit, um banco Room ou os dois: ela só observa o que o Repository expõe.

Detalhe que derruba muita gente

A Cloud Translation API tem duas versões: a Basic (v2), que aceita autenticação simples por API key (a que o guia usa) e a Advanced (v3), que exige OAuth2 ou Application Default Credentials e não aceita API key. Se você trocar de versão sem perceber essa diferença, a autenticação simplesmente para de funcionar.

Vale notar também que Retrofit não faz chamadas HTTP diretamente: ele transforma uma interface Kotlin/Java anotada (com @GET, @POST etc.) em um objeto chamável, delegando o transporte real para o OkHttp por baixo.

MÓDULO 03b

DiffUtil: o algoritmo que anima só o que mudou

Foto: Ingmar em Unsplash

Antes do DiffUtil, atualizar uma lista significava chamar notifyDataSetChanged(): que redesenha absolutamente tudo, mesmo que só um item tenha mudado. O DiffUtil usa uma variação do algoritmo de diff do Myers (o mesmo princípio por trás de git diff) pra comparar a lista antiga com a nova e calcular o menor conjunto de inserções, remoções e atualizações necessário.

O ListAdapter já embute essa lógica: basta estender a classe e chamar submitList() a cada nova versão dos dados. Por baixo, ele roda o cálculo de diff numa thread de background, então nem trava a UI durante listas grandes.

Um cuidado com cliques

O listener de clique deve ser configurado dentro de bind() (chamado toda vez que o ViewHolder é reciclado para um novo item) nunca em onCreateViewHolder(), que roda só quando uma célula nova é criada do zero. Colocar o listener no lugar errado é a causa mais comum de "cliquei no item 3 mas a ação foi do item 8" em listas Android.

MÓDULO 04

Segurança de credenciais: o que o local.properties não resolve sozinho

Foto: Sora Sagano em Unsplash

Guardar a chave em local.properties e lê-la via buildConfigField resolve um problema real: a chave para de aparecer em texto puro no código-fonte versionado. Mas vale ter os pés no chão sobre o que isso não resolve: um APK publicado pode ser descompilado, e uma chave embutida no BuildConfig ainda é recuperável por quem sabe procurar. É proteção contra vazamento acidental no Git, não contra engenharia reversa deliberada.

Por isso o Google recomenda uma segunda camada: restringir a própria chave no console do Cloud, associando-a ao nome do pacote do app e à impressão digital SHA-1 do certificado de assinatura. Mesmo que alguém extraia a chave do APK, ela só funciona nesse app específico.

O que a OWASP chama de M1

No Mobile Top 10 da OWASP, "uso impróprio de credenciais" (chaves fixas no código, segredos mal armazenados) aparece como uma das categorias mais recorrentes de vulnerabilidade em apps móveis: não é um detalhe menor, é um dos riscos mais comuns na prática.

Para segredos realmente sensíveis (não só uma chave de API com cota limitada, mas credenciais de produção), times mais maduros costumam ir além do local.properties: variáveis de ambiente injetadas em CI/CD, ou até criptografia do valor antes de embuti-lo no binário. O ponto de partida do guia: local.properties + .gitignore: já cobre o erro mais comum e mais caro: a chave commitada por acidente.

A camada de rede merece o mesmo cuidado: usar HttpsURLConnection ou uma lib que já valida certificado (Retrofit/OkHttp fazem isso por padrão) evita boa parte dos ataques de interceptação. E do lado do binário, ativar minifyEnabled true liga o R8, que renomeia classes e métodos para nomes curtos: não impede engenharia reversa por completo, mas eleva bastante o custo de quem tentar.
