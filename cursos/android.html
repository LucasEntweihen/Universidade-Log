Fundamentos & Navegação

Antes de desenhar telas bonitas, vale entender como o Android as gerencia por baixo dos panos: e como elas conversam entre si.

Foto: Peter Thomas em Unsplash

Gnomo

Bem-vindo à trilha! Vamos começar pelo que sustenta tudo o resto: como uma tela nasce, vive e é destruída. Estrutura é tudo.

O ciclo de vida de uma Activity

Uma Activity nunca é "aberta e fechada" de forma simples: ela transita por estados que o próprio sistema controla: onCreate → onStart → onResume → onPause → onStop → onDestroy. Entender esses callbacks é o que evita vazamento de memória, perda de dados numa rotação de tela e crashes ao voltar de segundo plano.

override fun onPause() {
    super.onPause()
    // salve aqui o que não pode se perder: o sistema pode matar o processo a qualquer momento depois disso
}

Intents: o mensageiro do Android

Um Intent descreve uma ação a ser realizada: abrir outra tela, compartilhar um texto, disparar a câmera. Pode ser explícito (você diz exatamente qual Activity abrir) ou implícito (você descreve a ação e o sistema escolhe o app capaz de atendê-la).

val intent = Intent(this, DetalheActivity::class.java)
intent.putExtra("id_produto", 42)
startActivity(intent)

Bundle: a mochila de dados

O Bundle é o contêiner que carrega pequenos dados dentro de um Intent, ou preserva o estado de uma tela durante onSaveInstanceState. Prefira tipos simples (String, Int, Parcelable): não é feito para objetos pesados.

val id = intent.getIntExtra("id_produto", -1)
// -1 é o valor padrão caso a chave não exista
Quiz rápido: Qual callback do ciclo de vida é o lugar mais seguro pra salvar dados antes da Activity poder ser destruída pelo sistema?
Encontre o bug
class MainActivity : AppCompatActivity() {
    companion object {
        var instanciaAtual: MainActivity? = null
    }
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        instanciaAtual = this
    }

Qual é o problema neste trecho?

Erro comum: guardar Context em variável estática

Uma Activity ou View presa numa variável static/companion object nunca é liberada pelo garbage collector, mesmo depois de destruída: é uma das causas mais comuns de OutOfMemoryError em apps que crescem. Se precisa de acesso global, use applicationContext, nunca a Activity inteira.

Componentes de UI & View Binding

Os blocos mais básicos de qualquer tela: e a forma moderna e seguindo de conectá-los ao código sem findViewById.

Foto: Nastia Petruk em Unsplash

TextView, Button, ImageView

São os três componentes que aparecem em praticamente toda tela Android: TextView exibe texto, Button captura cliques, ImageView exibe imagens locais ou baixadas. Simples isoladamente: o design entra em como você os combina dentro de um layout.

View Binding: adeus, findViewById

Antes, cada view exigia um findViewById manual: sujeito a erro de digitação no ID e sem checagem de tipo. Com View Binding ativado, o Android Studio gera uma classe Binding para cada XML, com uma referência direta e já tipada pra cada view com ID.

// build.gradle
android { buildFeatures { viewBinding = true } }

// na Activity
private lateinit var binding: ActivityMainBinding
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    binding = ActivityMainBinding.inflate(layoutInflater)
    setContentView(binding.root)
    binding.meuBotao.setOnClickListener { /* clique seguro, sem cast */ }
}

Splash Screen

A tela de abertura não deveria ser mais uma Activity com Thread.sleep(): a API moderna de Splash Screen exibe o ícone do app instantaneamente enquanto o processo ainda está sendo preparado, sem atrasar artificialmente a inicialização.

Quiz rápido: Qual a principal vantagem do View Binding sobre o findViewById tradicional?
Encontre o bug
class DetalheFragment : Fragment(R.layout.fragment_detalhe) {
    private lateinit var binding: FragmentDetalheBinding
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        binding = FragmentDetalheBinding.bind(view)
    }
}

Qual é o problema neste Fragment?

Erro comum: esquecer de limpar o binding no Fragment

Diferente de uma Activity, a View de um Fragment pode ser destruída (onDestroyView) enquanto o Fragment em si continua vivo. Se o binding não for anulado nesse momento, a View antiga fica presa na memória. O padrão seguro usa uma propriedade nullable e limpa em onDestroyView.

Layouts & Densidade de Tela

Construir hierarquias de visualização que se comportam bem em qualquer hardware: sem pixels fixos, sem surpresas.

Foto: Ingmar em Unsplash

DP vs. PX: por que isso importa

A regra de ouro: 1 DP = 1 PX numa tela de referência de 160 DPI. Em telas mais densas, o Android escala automaticamente os componentes para manter o mesmo tamanho físico: é isso que impede que seu botão fique minúsculo num celular caro e gigante num modelo de entrada.

1x
mdpi · 160 dpi (base)
1.5x
hdpi · 240 dpi
2x
xhdpi · 320 dpi
3x
xxhdpi · 480 dpi

Dica: use sp (scale-independent pixels) só para texto: ele também respeita o tamanho de fonte que a pessoa configurou no aparelho.

ConstraintLayout: as linhas onduladas

No editor visual do Android Studio, aquelas linhas onduladas não são só estética: representam as constraints: a elasticidade e a margem da conexão entre a View e o pai ou os componentes irmãos. É o que permite montar telas fluidas sem aninhar dezenas de layouts.

<!-- ancorando um botão nas quatro direções -->
<Button
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    app:layout_constraintTop_toTopOf="parent"
    app:layout_constraintStart_toStartOf="parent"
    app:layout_constraintEnd_toEndOf="parent"
    app:layout_constraintBottom_toBottomOf="parent" />

Outros tipos de layout (para reconhecer no mapa mental)

LayoutQuando usar

Qual é o problema neste trecho?

Erro comum: weight sem 0dp

Quando se usa layout_weight, a largura (num LinearLayout horizontal) deveria ser 0dp, não wrap_content. Com wrap_content, o sistema mede o conteúdo primeiro e só depois distribui o peso: um passo de medição extra e desnecessário em cada frame de layout.

Módulo 04 / 11

Temas & Design System

Centralizar a identidade visual num único lugar em vez de espalhar estilo por dezenas de arquivos de layout.

Foto: Nastia Petruk em Unsplash

Declarando um tema (res/values/themes.xml)

Toda declaração precisa de um name exclusivo e, obrigatoriamente, de um parent: é a herança que evita reescrever tudo do zero.

<!-- herda a base sólida do AppCompat -->
<style name="Theme.CustomApp" parent="Theme.AppCompat.Light.NoActionBar">
    <item name="colorPrimary">@color/brand_primary</item>
    <item name="android:windowBackground">@color/window_dark</item>
</style>

Vínculo no Manifest

O tema só passa a valer quando é referenciado no AndroidManifest.xml:

<application
    android:theme="@style/Theme.CustomApp">

Shapes customizados

Cantos arredondados e bordas em botões/dialogs pedem um XML de <shape> isolado, referenciado depois no tema:

<shape>
  <corners android:radius="20dp"/>
</shape>

Indo além: Custom Dialog

O mesmo raciocínio de shape + tema se aplica a caixas de mensagem customizadas. Você define o fundo em XML (cantos arredondados, cor sólida) e, no código, infla esse layout dentro de um Dialog: útil pra telas de "Você venceu" / "Você perdeu" ou qualquer feedback que não deveria ser um AlertDialog genérico.

val dialog = Dialog(this)
dialog.setContentView(R.layout.custom_dialog)
dialog.findViewById<Button>(R.id.btnOk).setOnClickListener {
    dialog.dismiss()
}
dialog.show()
Quiz rápido: Todo <style> customizado deve obrigatoriamente declarar qual atributo?
Encontre o bug
<Button
    android:textColor="#FFFFFF"
    android:background="#3F51B5" />

Qual é o problema neste trecho?

Erro comum: cor fixa em vez de atributo de tema

Usar #FFFFFF direto no XML "funciona", mas quebra o dark mode e a consistência visual. O caminho certo é referenciar um atributo do tema como ?attr/colorPrimary ou um recurso semântico em colors.xml: aí a cor muda sozinha quando o tema muda.

Módulo 05 / 11

RecyclerView de Alta Performance

A ferramenta certa pra qualquer lista: do feed mais simples ao catálogo com milhares de itens.

Foto: Ingmar em Unsplash

Adapter + ViewHolder, a dupla essencial

O RecyclerView não desenha mil views pra uma lista de mil itens: ele recicla um punhado de views visíveis na tela. O ViewHolder guarda as referências de cada célula, e o Adapter decide o que colocar nelas conforme o usuário rola a lista.

class ItemViewHolder(val binding: ItemProdutoBinding) :
    RecyclerView.ViewHolder(binding.root)

class ProdutoAdapter(private val itens: List<Produto>) :
    RecyclerView.Adapter<ItemViewHolder>() {
    override fun onBindViewHolder(holder: ItemViewHolder, position: Int) {
        holder.binding.tvNome.text = itens[position].nome
    }
}

Cliques e swipe-to-delete

Cliques são repassados via uma lambda no construtor do Adapter: nunca dentro de onCreateViewHolder, que só roda quando uma nova célula é criada, não a cada rebind. Deletar com gesto de swipe usa ItemTouchHelper anexado ao RecyclerView.

ListAdapter + DiffUtil

DiffUtil compara a lista antiga com a nova e calcula o menor conjunto de mudanças: em vez de redesenhar tudo, anima só o que de fato mudou. O ListAdapter já embute isso: basta chamar submitList().

Onde colocar o listener

Sempre dentro de bind(), não em onCreateViewHolder: o holder é reciclado, e um listener preso à posição errada é uma das causas mais comuns de "clique no item errado" em listas Android.

Coroutines: a corrida sem travar a tela

Uma chamada de rede na thread principal trava a UI e pode gerar um ANR. Coroutines resolvem isso com funções suspend que pausam sem bloquear a thread. No Android, prefira escopos que já respeitam o ciclo de vida: viewModelScope numa ViewModel, lifecycleScope numa Activity/Fragment.

viewModelScope.launch {
    val resultado = repository.traduzir(texto)
    _uiState.value = resultado
}

WebView: HTML dentro do app

Quando uma tela precisa renderizar conteúdo web (uma política de privacidade, um checkout, um artigo), o WebView embute um navegador dentro do próprio app: sem precisar abrir o Chrome. Vale lembrar: JavaScript vem desabilitado por padrão, e precisa ser ligado explicitamente se a página depender dele.

Configurando a API no Google Cloud Console

Criar um projeto

Todo recurso do Google Cloud vive dentro de um projeto: é o contêiner que agrupa faturamento, permissões e APIs ativadas.

Ativar a Cloud Translation API

Na biblioteca de APIs do console, procure e ative o serviço antes de tentar chamá-lo: API não ativada retorna erro 403.

Escolher a credencial certa

API Key é suficiente para acesso simples (a versão Basic/v2 usada neste guia). OAuth 2.0 entra quando o app precisa agir em nome de um usuário ou acessar a versão Advanced/v3 da API.

Fragments & Modularização

Telas reutilizáveis que se encaixam dentro de uma Activity: a peça que faltava pra layouts adaptáveis de verdade.

Foto: Emma Swoboda em Unsplash

Laura

Sistemas sólidos crescem sem quebrar. Um Fragment mal isolado hoje é um bug de estado compartilhado amanhã. Modularize com intenção, não por hábito.

Um pedaço de UI com vida própria

Um Fragment tem seu próprio ciclo de vida, mas vive hospedado dentro de uma Activity. Isso permite montar uma tela de tablet com duas colunas (lista + detalhe, cada uma um Fragment) e reaproveitar a coluna de detalhe sozinha no celular: mesma lógica, dois arranjos visuais.

class DetalheFragment : Fragment(R.layout.fragment_detalhe) {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        // binding e lógica de UI aqui, não no construtor
    }
}
Por que isso conversa com MVVM

Fragments costumam compartilhar uma ViewModel com a Activity que os hospeda (via activityViewModels()), o que permite dois Fragments irmãos (lista e detalhe) trocarem dados sem se conhecerem diretamente.

Módulo 08 / 11

Segurança Mobile: Credenciais, Rede & Código

Sua API key é dinheiro andando por aí. Trate-a como tal: e vá além dela.

Foto: Sora Sagano em Unsplash

Diretriz crítica

Uma API Key jamais deve residir num repositório Git: público ou privado. Exposta, ela permite uso malicioso por terceiros sob o faturamento do seu próprio projeto. Segundo o guia de análise de segurança da UFC (Gomes, 2017), a proteção de ativos críticos é prioridade zero em qualquer projeto que consuma APIs pagas.

Protocolo de armazenamento seguro

Guarde a chave em local.properties

TRANSLATE_API_KEY=sua_chave_aqui: esse arquivo não sobe pro Git por padrão nos projetos Android Studio.

Leia e injete via build.gradle

Use o objeto Properties para ler o arquivo e gerar um buildConfigField em tempo de compilação.

Consuma via BuildConfig

BuildConfig.TRANSLATE_API_KEY no código: nunca a string crua espalhada por aí.

Confirme o .gitignore antes do primeiro commit

Garanta explicitamente a linha local.properties lá dentro: depois do primeiro push já é tarde.

// build.gradle (Module)
buildConfigField("String", "API_KEY", "\"${localProperties.getProperty('TRANSLATE_API_KEY')}\"")

OWASP Top 10 Mobile

Além de chaves expostas, a lista da OWASP cobre criptografia insuficiente, armazenamento inseguro de dados locais e comunicação de rede sem proteção: vale usá-la como checklist de revisão antes de publicar qualquer app.

SSL/TLS na prática

Use sempre HttpsURLConnection ou bibliotecas que já validam certificado (Retrofit/OkHttp fazem isso por padrão). Para uma camada extra, certificate pinning trava o app pra aceitar só o certificado esperado do seu servidor.

Ofuscação de código com R8

Mesmo com a chave fora do Git, um APK publicado pode ser descompilado. O R8 (padrão do Android Studio) reduz esse risco renomeando classes e métodos para nomes curtos e sem sentido, além de remover código morto. Ativa-se com uma linha no build.gradle de produção:

buildTypes {
    release {
        minifyEnabled true
        shrinkResources true
    }
}

Ferramentas & Extras

O que fica em volta do código principal: nuvem, listas infinitas e a lupa pra quando algo dá errado.

Foto: Zetong Li em Unsplash

Chud

"Melhor pedir pra IA...": Chud usa IA pra tudo e nunca entende o porquê. Não seja o Chud: use as ferramentas, mas entenda o que elas fazem por baixo.

Firebase & Cloudinary

Firebase cobre backend inteiro pra apps pequenos e médios: autenticação, banco em tempo real, storage, crash reporting. Cloudinary é mais especializado: upload, otimização e transformação de imagens/vídeos via URL, sem processar mídia no seu próprio servidor.

Paging 3

Pra listas realmente longas (milhares de itens), carregar tudo de uma vez é desperdício. A biblioteca Paging 3 busca só a "página" de dados que o usuário está prestes a ver, integrando direto com RecyclerView e Flow/LiveData.

Não vire o Dodô da sua stack

O dodô foi extinto por não conseguir se adaptar rápido o suficiente a um ambiente que mudou. Dependência desatualizada, biblioteca sem manutenção, versão do SDK travada há dois anos: é assim que um projeto "morre" tecnicamente sem que ninguém perceba até ser tarde. Revisitar e atualizar dependências de vez em quando não é perfeccionismo, é sobrevivência.

Logcat: a lupa de todo dev Android

Quando algo quebra, o Logcat é o primeiro lugar a olhar: um fluxo de mensagens do sistema e do seu próprio código, filtrável por tag e nível de severidade (Verbose, Debug, Info, Warn, Error).

Log.d("MinhaTag", "cheguei aqui com valor = $valor")
Log.e("MinhaTag", "deu ruim", excecao)

Sensores do aparelho: SensorManager (acelerômetro, giroscópio, luz)

Projeto Prático: Lista com Fotos

Juntando tudo (Retrofit, Coroutines, ViewModel, RecyclerView e Glide) numa única lista funcionando de ponta a ponta.

Foto: Sora Sagano em Unsplash

Jade

Todo sistema complexo é só um quebra-cabeça interessante disfarçado. Bora montar essa lista peça por peça: sem pressa pra acertar de primeira.

Uma forma simples de fixar quatro módulos de uma vez: pensar cada peça como um personagem com um papel único numa equipe de entrega.

Retrofit: o Motoboy

Faz a requisição na internet rodando em segundo plano (com Coroutines), pra não congelar a tela do usuário enquanto os dados chegam.

ViewModel: o Gerente

Recebe o JSON já transformado em dados, guarda em segurança e avisa a interface assim que a lista está pronta pra exibir.

Activity/Fragment: a Tela

Fica só observando o ViewModel. Quando os dados chegam, repassa direto pro Adapter: sem lógica de negócio aqui.

Adapter + Glide: os Pintores

O Adapter infla o layout de cada item da lista; o Glide baixa a imagem da URL e a exibe suavemente na célula, com cache automático.

O fluxo completo, em ordem

Retrofit (busca) → ViewModel (processa) → Activity (observa) → Adapter+Glide (exibe)
