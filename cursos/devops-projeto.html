Projeto Prático: A Frota Completa

Um walkthrough completo, camada por camada, do mesmo projeto sugerido no módulo 10: do primeiro commit até um Deployment rodando de verdade no seu cluster local.

Foto: Peter Thomas em Unsplash

Capitão Baba Grogue

Uma frota de verdade não nasce pronta. Nasce peça por peça: primeiro o marujo (container), depois a formação (compose), depois a esquadra inteira (Kubernetes). Bora montar a sua.

A tripulação do projeto

Cada arquivo tem um papel único: vale voltar aqui sempre que a arquitetura parecer abstrata demais.

O Talkie-Walkie

Passo 1: Empacote a aplicação (Dockerfile)

1

Escreva a receita do seu marujo

Uma API simples "Hello DevOps" em Node.js, por exemplo:

FROM node:20-alpine
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Construa e teste local antes de ir pro Compose: docker build -t frota-api . seguido de docker run -p 3000:3000 frota-api.

Passo 2: Forme a esquadra (Docker Compose)

2

Conecte a API a um banco de dados

version: "3.9"
services:
  api:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: exemplo
    volumes:
      - dados_db:/var/lib/postgresql/data
volumes:
  dados_db:

Suba tudo junto com docker compose up: a API já enxerga o banco pelo nome do serviço (db), sem descobrir IP nenhum na mão.

Passo 3: Escreva o mapa do tesouro (Kubernetes)

3

Declare o estado desejado da sua frota

apiVersion: apps/v1
kind: Deployment
metadata:
  name: frota-api-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frota-api
  template:
    metadata:
      labels:
        app: frota-api
    spec:
      containers:
        - name: api-marujo
          image: frota-api:latest
          ports:
            - containerPort: 3000

replicas: 3 declara que você sempre quer 3 marujos vivos rodando essa imagem: o Kubernetes se vira pra manter isso verdade, mesmo se um deles cair.

Passo 4: Dê as ordens (kubectl)

4

Aplique o plano e observe a frota nascer

kubectl apply -f deployment.yaml
kubectl get pods
kubectl get rs
kubectl describe pod <nome-de-um-pod>

Depois do apply, você deve ver 3 Pods no estado Running em poucos segundos. get rs mostra o ReplicaSet garantindo esse número.

Passo 5: O Desafio do Capitão (teste de resiliência)

5

Mate um Pod e documente a reconciliação

kubectl delete pod <nome-de-um-dos-pods>
kubectl get pods

Rode o segundo comando bem rápido depois do primeiro. Você vai ver um novo Pod nascendo pra substituir o que você acabou de matar: tire um print disso pra registrar no seu projeto. É a prova visual de que o Laço de Reconciliação está funcionando.

O fluxo completo, de novo

Commit & push no GitHub → docker build gera a imagem → docker-compose.yml valida localmente com dependências → deployment.yaml declara o estado desejado no cluster → kubectl apply lança tudo ao mar → o Laço de Reconciliação garante que o estado desejado se mantenha, mesmo quando algo falha.

Checklist de conclusão

Se todos esses pontos fazem sentido, o projeto está de pé:

  • Seu Dockerfile builda sem erro e o container roda local antes de ir pro Compose.
  • O docker-compose.yml sobe API + banco conectados, com volume persistente pro banco.
  • O manifesto de Deployment tem replicas, selector e labels coerentes entre si.
  • Você já testou matar um Pod na mão e viu a reconciliação em ação.
  • Você documentou no README quais permissões IAM mínimas essa aplicação precisaria numa AWS real.
