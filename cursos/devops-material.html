MÓDULO 01

Por que "cultura" é a palavra certa, e não "processo"

Foto: Peter Thomas em Unsplash

É tentador tratar DevOps como um checklist de processo: "implementamos CI/CD, logo somos DevOps". Mas o framework CAMS foi desenhado propositalmente com "Culture" na primeira letra, não por acaso alfabético. Automação sem cultura de colaboração vira só um monte de scripts que ninguém entende além de quem escreveu. Um pipeline de CI/CD brilhante não conserta um time onde Dev joga código "pronto" por cima do muro pro Ops descobrir os problemas sozinho, em produção, à uma da manhã.

É por isso que destruir silos vem antes de qualquer ferramenta na lista de prioridades. Um silo não é só uma estrutura organizacional: é um padrão de comunicação. Times em silo otimizam pra métricas locais ("meu código passou nos testes") em vez de métricas de sistema ("o usuário final teve uma boa experiência"). O CAMS ataca isso de frente: cultura de empatia primeiro, automação depois, mas nunca sem medição: porque sem métricas, ninguém sabe se a colaboração está realmente funcionando.

Um jeito prático de perceber silo

Se a resposta pra "por que esse bug chegou em produção?" é sempre "não era meu módulo", existe um silo ali: não importa quantas ferramentas de automação o time usa.

MÓDULO 02

Um commit não é um "salvar". É uma fotografia imutável.

Foto: Nastia Petruk em Unsplash

Internamente, o Git não guarda "diferenças" entre versões de arquivo do jeito que muita gente imagina: ele guarda snapshots. Cada commit aponta pra um estado completo da árvore de arquivos naquele instante, mais um ponteiro pro commit anterior (ou vários, no caso de um merge). É por isso que navegar pelo histórico do Git é rápido: não é preciso reconstruir uma sequência de patches, cada commit já é uma foto completa e independente.

A Staging Area existe justamente pra dar controle fino sobre o que entra em cada fotografia. Você pode ter editado três arquivos, mas só querer registrar as mudanças de um deles nesse commit: git add arquivo.js escolhe exatamente isso, deixando os outros dois de fora do snapshot até você decidir incluí-los.

Commit não é backup

Arquivos que nunca foram adicionados ao staging (com git add) não fazem parte de nenhum commit: não existe rede de segurança pra eles até você explicitamente decidir versioná-los.

MÓDULO 03

Um bom Pull Request é uma carta, não um dump de código

Foto: Emma Swoboda em Unsplash

Um PR sem descrição, com título "fix", força quem revisa a reconstruir sozinho todo o raciocínio por trás da mudança lendo linha por linha de diff. Um bom PR conta uma história: o que mudou, por que mudou, e como testar que funcionou. Isso não é burocracia: é a diferença entre uma revisão de 5 minutos e uma de 40.

Vale lembrar também que revisão de código é bidirecional: quem revisa não está caçando erro pra provar que é melhor, está protegendo o sistema como um todo. E quem recebe a revisão não deveria levar comentários pro lado pessoal: código não é extensão de identidade, é um artefato que o time inteiro é dono em conjunto.

MÓDULO 04

O motivo real de containers serem leves: o kernel compartilhado

Foto: Nastia Petruk em Unsplash

A diferença entre VM e container não é "tamanho do arquivo": é o que cada um virtualiza. Uma VM virtualiza hardware inteiro: CPU, memória, disco, e roda um Sistema Operacional Convidado completo por cima, com seu próprio kernel. Um container Docker usa recursos do kernel Linux do próprio hospedeiro: namespaces (isolamento de processos, rede, sistema de arquivos) e cgroups (limites de CPU/memória): pra criar a ilusão de isolamento sem duplicar o sistema operacional inteiro.

É por isso que subir um container leva segundos e subir uma VM leva minutos: o container não precisa passar pelo processo de boot de um SO completo, ele só inicia o processo da aplicação diretamente, já isolado pelo kernel compartilhado.

MÓDULO 05

O Laço de Reconciliação é um sistema de controle, não mágica

Foto: Sora Sagano em Unsplash

O comportamento "mate um Pod e outro nasce sozinho" parece mágica na primeira vez que você vê, mas é engenharia de sistemas de controle clássica: o Kubernetes roda, em loop contínuo, um controller que compara o estado desejado (o que está no seu YAML) com o estado observado (o que está rodando de verdade no cluster agora). Toda vez que há diferença, ele emite ações pra fechar essa diferença: criar um Pod, remover outro, redistribuir carga.

Isso é exatamente o mesmo princípio de um termostato: ele não "sabe" a temperatura ideal em algum sentido filosófico, ele só compara continuamente "temperatura atual" com "temperatura configurada" e liga/desliga o aquecedor até a diferença zerar. O Kubernetes faz isso com Pods, réplicas, volumes e praticamente todo recurso que ele gerencia.

Por que isso importa na prática

Entender que é um loop de comparação (não uma regra especial de "recriar Pod morto") explica por que o Kubernetes também reage a mudanças manuais indevidas: se alguém editar um recurso direto no cluster sem passar pelo manifesto, o controller pode "corrigir" essa edição de volta: porque, do ponto de vista dele, isso também é uma divergência do estado desejado.

MÓDULO 06

Menor privilégio: a regra que evita o pior tipo de incidente

Foto: Ingmar em Unsplash

Uma parte enorme dos incidentes de segurança em nuvem não vem de hackers sofisticados explorando zero-days: vem de credenciais com permissão demais, vazadas ou mal configuradas. O princípio do menor privilégio no IAM da AWS diz: cada usuário, aplicação ou serviço recebe exatamente as permissões que precisa pro seu trabalho, nem uma a mais.

Na prática, isso significa preferir roles específicas (ex: "essa Lambda só pode ler desse bucket S3 específico") em vez de políticas amplas ("essa Lambda pode fazer qualquer coisa em S3"). É mais trabalho de configuração inicial, mas transforma um vazamento de credencial de "catástrofe total" em "incidente contido".
